The exam

L5 Data Center is Arista's ACE Professional – Data Center credential. You can take the two Specialist exams (Operations AN-DC-OP01 and Engineering AN-DC-EN01) and get the Professional badge automatically, or sit the single Professional exam AN-DC-PR01, which mixes both. Each is a timed, proctored, open-book lab. You get a scenario in the same virtual environment the Arista Academy labs use: EOS switches with a CloudVision instance, and a list of tasks to build, fix, and verify. Arista does not publish weights, task counts, or the pass mark.

That shapes how to study. You are graded on the end state of the devices, not on what you can recite. Speed at the CLI, a habit of verifying every task, and knowing where to look things up matter more than memorized trivia.

How to sit a hands-on exam

  • Read every task before typing. Note dependencies (an EVPN task fails if the underlay task before it is wrong).
  • Draw the topology and fill in ASNs, loopbacks, VNIs and VRFs on scratch paper in the first ten minutes.
  • Make changes in a configure session so you can review the diff and abort a mistake.
  • Verify each task with its show command before moving on. Then write memory.
  • Never break management access or the CloudVision connection (TerminAttr, Management1, the MGMT VRF).
  • If a task asks for CloudVision, do it in CloudVision. A correct config pushed from the CLI shows up as out of compliance and may not score.
  • Skip a stuck task and come back. Leave 20 minutes at the end to re-verify everything.

Open book, used well

  • The EOS User Manual is searchable. Practise finding a feature's config chapter in under a minute.
  • On the switch, ? and show running-config all | section <feature> show every option and its default.
  • show running-config | section router bgp and show active (inside a mode) keep you oriented.
  • This guide's show-command sheet is meant to be open beside the exam.
  • Check the current exam policies on training.arista.com for what materials are allowed.

EOS Management

Changing a running switch safely, upgrading it without an outage, and getting it back when it won't boot. EOS keeps all state in SysDB and runs each feature as a separate agent, which is why an agent can restart without a reload and why config sessions and rollback work so well.

1.1

EOS operations and safe change

Know

  • SysDB is the central state database. Agents (Bgp, Stp, Lag…) publish to it and read from it. show agent, show processes top.
  • EOS is Linux. bash drops you to a shell; FastCli -p 15 -c "cmd" runs CLI from bash.
  • Config sessions stage changes, show a diff, and commit atomically. commit timer rolls back unless you confirm.
  • Checkpoints save a named copy of the running config; configure replace swaps the whole running config for another file and applies only the differences.
  • Maintenance mode drains traffic from a switch before work: BGP sends a lower preference or withdraws, MLAG and interfaces can be quiesced.

Configure

configure session add-vlan40
   vlan 40
      name APP
   interface Ethernet3
      switchport trunk allowed vlan add 40
   show session-config diffs
   commit timer 00:05:00      ! auto-rollback in 5 min
! still reachable? confirm it:
configure session add-vlan40 commit

configure checkpoint save pre-change
configure replace checkpoint:pre-change
! drain a switch before work
maintenance
   unit System
      quiesce

Verify

  • show configuration sessions detail
  • show config checkpoints · show running-config diffs
  • show maintenance · show maintenance summary

Exam traps

  • Forgetting write memory. A reload or a CloudVision reconcile will wipe unsaved work.
  • Leaving a session uncommitted. Changes in a session do nothing until commit.
  • configure replace with a file that lacks management config drops your access.

1.2

EOS upgrades: standard, SSU, MLAG ISSU

Know

  • Standard upgrade: copy the .swi to flash, check its hash, set boot system, save, reload. Outage equals reload time.
  • Smart System Upgrade (SSU, reload fast-boot) keeps the data plane forwarding while the control plane restarts on supported fixed platforms. Check first with show reload fast-boot.
  • MLAG ISSU: upgrade the secondary first, then the primary. Hosts stay up on the other peer. Check show mlag issu compatibility, fix config-sanity, then upgrade, wait for MLAG active-full and for reload-delay to expire, then do the peer. AW 18 p.96
  • Plain reload prints MLAG ISSU warnings (STP not yet restartable, active-partial MLAGs, reload-delay below the recommended value, peer ports still errdisabled). Read them; reload now skips them. AW 18 p.97
  • Chassis with two supervisors: upgrade the standby, switch over (SSO), then the other.
  • CloudVision upgrades use an image bundle assigned to a container or device, which creates a task you run in a change control.

Configure

copy scp://user@10.0.0.10/EOS-4.32.2F.swi flash:
verify /sha512 flash:EOS-4.32.2F.swi
boot system flash:EOS-4.32.2F.swi
write memory
show boot-config
reload                  ! or: reload fast-boot

! MLAG pair, before each peer
show mlag issu compatibility flash:EOS-4.32.2F.swi
show mlag detail | include State|delay
show mlag config-sanity
show spanning-tree bridge detail | include agent
! "Stp agent restartable : True" before reload

Verify

  • show version · show boot-config
  • show mlag (state: active, negotiation: connected, ports active-full)
  • show mlag interfaces detail during reload-delay

Exam traps

  • Upgrading both MLAG peers at once, or the second before the first has finished its reload-delay (its ports still errdisabled).
  • Using reload now during an MLAG upgrade and missing the warnings.
  • Not saving after boot system; the old image boots again.
  • Not enough flash. Check dir flash: and delete old images first.

1.3

Extensions, Aboot and recovery

Know

  • Extensions (.swix/.rpm) add features or hotfixes. Install, then copy to boot-extensions so they survive a reload. TerminAttr is an extension.
  • Aboot is the bootloader. Press Ctrl-C at boot to get the Aboot# shell and boot an image by hand.
  • Lost password: from Aboot, rename /mnt/flash/startup-config and boot. The switch comes up with no config.
  • fullrecover in Aboot wipes flash back to factory. Last resort.
  • Health: show version (free memory), dir flash:, show agent logs crash, show logging.

Configure

copy https://10.0.0.10/TerminAttr-1.30.swix extension:
extension TerminAttr-1.30.swix
copy installed-extensions boot-extensions
show extensions

! Aboot shell (Ctrl-C during boot)
Aboot# cd /mnt/flash
Aboot# mv startup-config startup-config.old
Aboot# boot flash:EOS-4.32.2F.swi

Verify

  • show extensions (status should be A, I: available and installed)
  • show boot-extensions

Exam traps

  • Installing an extension but not adding it to boot-extensions.
  • Extension built for a different EOS architecture (32/64-bit) shows as not installable.

Practice: D1

You must change an uplink's VLAN list remotely and might lock yourself out. What do you type?

Use configure session NAME, make the change, check show session-config diffs, then commit timer 00:05:00. If you can still reach the switch, run configure session NAME commit to keep it. If not, it rolls back by itself.

leaf1 and leaf2 are an MLAG pair. In what order, and when, do you upgrade them?

Check ISSU compatibility. Upgrade one peer (often the secondary). Wait until show mlag is active/connected, all MLAG ports are active-full, and reload-delay has expired. Then upgrade the other peer. Hosts dual-homed by LACP stay up throughout.

A hotfix extension is installed but gone after a reload. Why?

It was never copied into boot-extensions. Run copy installed-extensions boot-extensions.

CloudVision Operations

CloudVision is where you onboard devices, push config through reviewed change controls, and roll back. There are two provisioning models: the classic one (containers and configlets) and Studios (workspaces, inputs and tags). The exam can ask for either.

2.1

CloudVision overview, setup and onboarding

Know

  • CVP is on-premises (single node or a three-node cluster). CVaaS is Arista's hosted service. Same features, different onboarding address and token.
  • Devices stream state to CloudVision through the TerminAttr agent over gRPC. Provisioning uses eAPI or gNMI back to the device.
  • Onboarding: install TerminAttr, configure it with the CV address, auth token and VRF, then the device appears in Inventory.
  • Admin tasks: backup and restore (cvpi backup), upgrades, licensing, user roles and service accounts.

Configure

daemon TerminAttr
   exec /usr/bin/TerminAttr -cvaddr=192.168.0.5:9910
      -cvauth=token,/tmp/token -cvvrf=MGMT
      -smashexcludes=ale,flexCounter,hardware,kni,pulse,strata
      -ingestexclude=/Sysdb/cell/1/agent,/Sysdb/cell/2/agent
      -taillogs
   no shutdown
! CVaaS: -cvaddr=apiserver.arista.io:443
!        -cvauth=token-secure,/tmp/cv-onboarding-token

management api http-commands
   no shutdown
   vrf MGMT
      no shutdown

Verify

  • show daemon TerminAttr (look for "connected")
  • show management api http-commands
  • CloudVision: Devices > Inventory shows the device as streaming

Exam traps

  • Wrong VRF in -cvvrf; TerminAttr can't reach CV over the default VRF.
  • Token file missing or expired. Onboarding tokens are time-limited.
  • Clock skew breaks TLS. Configure NTP first.

2.2

Provisioning: containers, configlets, change control, rollback, ZTP

Know

  • Containers form a tree under Tenant. Configlets on a container apply to every device below it. Device configlets apply to one device.
  • Designed config is the merge of all configlets that apply to a device. Running config is what the device has. CloudVision flags differences as out of compliance.
  • Reconcile captures running-config lines that no configlet owns into a reconcile configlet, so the next push won't remove them.
  • Any change creates a task. Tasks go into a change control with stages run in series or in parallel, a review, an approval, and execution.
  • Snapshots capture show-command output before and after a change. Rollback returns a device (or the whole network) to an earlier config and image.
  • Configlet builders are Python with a form that generate per-device configlets (hostname, IPs) from inputs.
  • Image bundles hold an EOS image plus extensions and are assigned like configlets.
  • ZTP: a factory-default switch gets DHCP with a bootfile URL pointing to CVP, registers, and lands in the Undefined container. ZTR (replacement) gives a new switch the config of the one it replaces.

Workflow

# Classic provisioning, in order
1  Provisioning > Network Provisioning
2  Move device: Undefined -> DC1/Leaf
3  Container "Leaf": add configlet BASE-LEAF
4  Device leaf1: add configlet leaf1-INTF
5  Review designed vs running, Save
6  Tasks -> Create Change Control
7  Stages: series or parallel, add snapshot
8  Review & approve -> Execute
9  Compare snapshots; roll back if needed

# ZTP DHCP (ISC dhcpd)
option bootfile-name
  "http://192.168.0.5/ztp/bootstrap";

Verify

  • Inventory compliance column is green for the devices you touched.
  • Change control shows every task as completed.
  • On the device: show running-config matches the designed config.
  • ZTP: show zerotouch on the switch, and the device appears in Undefined.

Exam traps

  • Making the change on the CLI, then pushing from CloudVision: CloudVision removes lines it doesn't know. Reconcile first.
  • Creating tasks but never executing the change control.
  • Two configlets that set the same line with different values; the last one in order wins.
  • Moving a device to a new container drops the old container's configlets.

2.3

Studios for operations: workspaces, tags, Day-2

Know

  • Studios turn intent (inputs in a form) into config. A workspace is a sandbox, like a git branch: you edit studios and tags in it, Start Build, review the proposed config per device, then Submit, which creates a change control.
  • Tags are key:value labels on devices or interfaces (DC:DC1, Role:Leaf). Studios use tag queries to select what they apply to. System tags are automatic; user tags you create.
  • The Inventory and Topology studio decides which devices Studios manage. Start there.
  • The Static Configuration studio holds plain configlets in the Studios world, assigned by tag or device.
  • Other operational studios: Date and Time, Authentication, Software Management (images), Interface Configuration.
  • Day-2 change = open a workspace, change one input, build, review the diff, submit, approve the change control.

Workflow

1  Workspaces > New workspace "add-ntp"
2  Studios > Date and Time
3  Apply to tag query:  Role:Leaf OR Role:Spine
4  NTP server 192.168.0.1, VRF MGMT
5  Start Build  -> check proposed config
6  Submit       -> change control created
7  Change Control: Review & Approve, Execute

# Tag queries
DC:DC1 AND Role:Leaf
Role:Leaf AND NOT device:leaf4

Verify

  • Build status green for every device; no "Configuration Validation" errors.
  • Change control complete; devices compliant.
  • show running-config | section ntp on a leaf.

Exam traps

  • Editing a studio but never submitting the workspace. Nothing reaches the devices.
  • Device not added to Inventory and Topology studio, so other studios ignore it.
  • Mixing classic configlets and Studios on one device without knowing which wins. Studio config and static configlets merge; conflicting lines fail validation.

Practice: D2

A colleague added a banner on leaf2 via CLI. You must push a new configlet from CloudVision without losing it. What first?

Reconcile leaf2. CloudVision builds a reconcile configlet with the banner line so the designed config includes it. Then add your configlet and push through a change control.

Ten new leaves arrive factory-fresh. How do they get to the right config with no console work?

ZTP: DHCP hands each switch a bootfile URL on CVP, they register into the Undefined container, you move each to its container (inheriting configlets), add device configlets or a builder, assign the image bundle, and execute the change control.

What does Submit in a Studios workspace actually do?

It merges the workspace into mainline and creates a change control with one task per affected device. Nothing is pushed until that change control is approved and executed (unless auto-approve is configured).

Monitoring and Troubleshooting

EOS can watch itself and act (scheduler, event monitor, event manager), stream to CloudVision, and give you packet-level tools without a probe. Expect tasks like "capture X when Y happens" and "find why host Z can't reach W".

3.1

Advanced Event Management

Know

  • Scheduler runs a CLI command on an interval and keeps rotating log files in flash. The built-in tech-support schedule runs hourly.
  • Event monitor records MAC, ARP, route, LACP, MRoute and other table changes into a local SQLite database you can query later.
  • Event manager (event-handler, Arista's equivalent of Cisco EEM) runs a bash action on a trigger: on-boot, on-intf, on-logging (regex), on-counters, on-maintenance, on-startup-config, vm-tracer. AW 27 p.143
  • An on-intf action gets variables such as $INTF, $OPERSTATE and $IP-PRIMARY. For several CLI commands, put them in a script on flash and call it from the action. AW 27 p.145
  • Actions can call FastCli, send email (ch. 22), or write to flash.

Configure

schedule cfg-backup interval 60 max-log-files 24 command show running-config

event-monitor          ! on by default; buffers MAC/ARP/route
show event-monitor mac match-mac 0050.5600.0001
show event-monitor route match-ip 10.10.10.0/24

event-handler UPLINK-DOWN
   trigger on-intf Ethernet1 operstatus
   delay 5
   action bash FastCli -p15 -c "show interfaces Ethernet1" > /mnt/flash/e1-down.txt

event-handler CPU-BUSY
   trigger on-counters
      poll interval 10
      condition tcollector.proc.stat.cpu.type=idle < 30
      threshold 60 count 3      ! 3 hits within 60 s
      action bash logger -p local4.warning "CPU idle below 30%"
! counter names vary by platform:
! show event-handler trigger counters | grep idle

event-handler SAVE-HISTORY
   trigger on-startup-config
   delay 0                    ! catch rapid back-to-back saves
   action bash /mnt/flash/save-startup-copy.sh

Verify

  • show schedule summary · dir flash:schedule/cfg-backup
  • show event-handler (trigger, action, last trigger time, counts; includes the built-in DropCountersHandler) AW 27 p.147–148
  • show event-handler trigger counters (counters available to on-counters)
  • show event-monitor sub-commands; event-monitor interact for SQL

Exam traps

  • Pick delay on purpose: a longer delay damps a flapping link, while delay 0 is needed when triggers come in quick succession, or some are missed. AW 27 p.147
  • A handler only takes effect when you exit its config mode, and on-boot and on-intf handlers fire once at that moment. AW 27 p.143, 146
  • EOS accepts a broken action without complaint. Check show event-handler <name> and the log (EVENT_ACTION_FAILED with an exit code). AW 27 p.146
  • on-startup-config fires on write memory or copy running-config startup-config, not when someone edits the file in bash. AW 27 p.145
  • Bash quoting inside action bash. Test the command in bash first.
  • Scheduler interval is in minutes.

Arista Warrior ch. 27, Event Manager: notes by page (real-world depth; a long shot on the exam)

  • p.143 An event handler is a trigger plus an action, with an optional delay. Example use: email the server team whenever the port to a flaky server goes down. The trigger types are listed above. on-counters works on ASIC and system counters, thousands of them, and the names depend on the platform: list them with show event-handler trigger counters and filter with grep.
  • p.145 on-intf can watch IP, IPv6, or operational status; listing more than one means "any of them". on-logging matches a regex against the log with a poll interval. on-maintenance fires on entering or leaving maintenance mode. Handler options: action, asynchronous, delay, threshold, timeout, and a free-text comment.
  • p.146 A typo in the action (in the book, an email command missing its recipient) is accepted. The handler fires, the log records the failed action and its exit code, and show event-handler shows the action string so you can spot the mistake.
  • p.146 An on-counters handler polls on an interval and compares a condition; threshold with a count requires several matches inside a window, so spiky values like CPU don't fire constantly. The condition can also be the output of a bash command. CloudVision is the better CPU monitor; this is the on-box fallback.
  • p.147 The book's on-startup-config example copies startup-config to a timestamped file on every save, a cheap change history. Rapid saves were missed until delay 0 was set. Watch flash space if you do this, or copy the files off-box; AAA command accounting is the more complete answer.
  • p.147–148 show event-handler lists every handler with its trigger, action, polls, and when it last fired. EOS ships a built-in handler, DropCountersHandler, that polls drop counters and logs when they rise.

Monitoring with CloudVision

Know

3.3

EOS monitoring tools

Know

  • SNMP: prefer v3 with auth and privacy. Bind to the MGMT VRF.
  • sFlow: sampled packet headers plus counters to a collector. Good for top talkers.
  • LANZ: sub-millisecond queue-depth reporting from the ASIC. SNMP graphs average over 5 minutes and hide microbursts that fill buffers and drop packets. LANZ only reports; it doesn't change how traffic flows. Hardware-only, so not in vEOS or cEOS. AW 23 p.123
  • Port mirroring: local SPAN, remote via GRE, or to the CPU so you can run tcpdump on the switch.
  • TAP aggregation: turns a switch into a packet broker. Tap ports (receive only) bring in copies of traffic; tool ports (transmit only) feed analyzers; aggregation groups join them. Real-world depth, not tested on the lab exam. AW 26 p.140–141
  • watch re-runs a command every N seconds; useful on counters.

Configure

snmp-server vrf MGMT
snmp-server group RO v3 priv
snmp-server user mon RO v3 auth sha AuthPass priv aes PrivPass

sflow sample 16384
sflow destination 192.168.0.20
sflow source-interface Management1
sflow run

queue-monitor length                  ! LANZ on, globally
queue-monitor length notifying        ! S/U/E records instead of polling
interface Ethernet48
   queue-monitor length thresholds 40962 10241   ! high low, bytes
show queue-monitor length status
show queue-monitor length Ethernet48
show queue-monitor length csv > flash:lanz.csv

monitor session CAP source Ethernet5 both
monitor session CAP destination Cpu
bash sudo tcpdump -i mirror0 -nn -c 50

tcpdump interface Ethernet1 filter icmp   ! CPU-bound only
watch 2 show interfaces Ethernet1 counters rates

Verify

  • show sflow · show snmp user
  • show monitor session
  • show queue-monitor length status (mode, per-port thresholds) · show tap aggregation groups

Exam traps

  • tcpdump on a front-panel interface only sees traffic to or from the CPU. Mirror to Cpu to see transit traffic.
  • sFlow source in the wrong VRF; datagrams never reach the collector.
  • TAP aggregation mode exclusive turns all switching off on that switch.
  • LANZ thresholds: on some platforms tab-completing gives threshold (singular), which sets only the high mark. Type thresholds <high> <low>. Units differ by platform (bytes on newer ASICs, buffer segments on older ones); check with ?. AW 23 p.125
  • Writing CSV output to a non-persistent location; save to flash: if it must survive a reboot. AW 23 p.126

Arista Warrior ch. 23, LANZ: notes by page

  • p.123 show interfaces has no buffer information because buffer state changes faster than you can read it. Throughput from SNMP is the difference between two octet counters divided by the poll interval, so a calm 5-minute average can hide a second full of bursts over line rate. LANZ reads queue depth from the ASIC at sub-millisecond granularity, on supported hardware only.
  • p.123–124 Model a port buffer as a tank filled faster than it drains. LANZ uses a high and a low queue threshold: crossing the high mark logs a Start (S) record, Update (U) records follow while it stays congested, and dropping under the low mark logs an End (E) record. LANZ watches the buffer; it doesn't do flow control.
  • p.124 Two modes. Polling (P records, roughly "was there congestion in the last second") is the default on some platforms such as the 7280R. Notifying mode gives the detailed S/U/E records but uses more hardware resources.
  • p.124–125 The book's lab makes congestion on demand: a static-route loop between two switches, one port shaped down to 5 Gbps with shape rate, then a burst of UDP from iperf in bash. load-interval 1 makes the interface rates readable second by second.
  • p.125 Enable LANZ globally with queue-monitor length, then set per-interface thresholds (high then low). show queue-monitor length status shows the mode and every port's thresholds. show queue-monitor length <intf> shows the records with queue length and duration.
  • p.125 The Ingress Port-set column lists every port on the same ASIC core as the congested port, so it narrows down where the burst came in, not the exact port. show platform jericho mapping shows the port-to-core mapping on Jericho-based switches.
  • p.126 For analysis, CloudVision graphs LANZ data, and it can be streamed out (Google Protocol Buffers). Without those, the csv keyword dumps up to the last 100,000 over-threshold events, oldest first; redirect it to a file on flash: and open it in a spreadsheet.

Arista Warrior ch. 26, Tap Aggregation: notes by page (real-world depth, not tested on the lab exam)

  • p.140 TapAgg lets a non-blocking Arista switch do the job of a dedicated packet broker: many taps or SPAN feeds in, a few analyzers out. mode exclusive takes the whole fixed switch out of normal switching (every port goes errdisabled until set to tap or tool), so never try it on a production switch. Modular chassis can use mixed mode and give only some linecards to TapAgg.
  • p.140 In TapAgg mode the switch stops sending STP, LLDP and similar control traffic on tap and tool ports, and MAC learning and flooding are off on them. ACLs, QoS and LAGs still work, and tap or tool ports can be port-channels.
  • p.140–141 A tool port can belong to several groups; a tap port has one default group. Tool ports use switchport tool group set (or add/remove); tap ports use switchport tap default group. Tap ports also have options for allowed VLANs, native VLAN, identity tagging and truncation.

Layer 2 and Layer 3 Designs

Two fabric shapes. L2LS keeps the spines as a Layer 2/3 boundary with MLAG, so STP sees no loops. L3LS routes every leaf-to-spine link, uses ECMP, and carries Layer 2 over VXLAN where it's needed.

4.1

L2LS: VLANs, STP, LACP, MLAG, VARP/VRRP

Know

  • EOS default STP is MSTP. Keep the spines (MLAG pair) as root; edge ports get portfast and BPDU guard.
  • MLAG makes two switches look like one LACP partner: both send the same chassis ID, so the downstream device just sees a normal port-channel and knows nothing about MLAG. AW 18 p.89, 91
  • The peer link is an ordinary trunk port-channel (use at least two members). VLAN 4094 goes in a trunk group so it rides only the peer link, and its SVI gets no autostate so it stays up. AW 18 p.90
  • Domain ID is case-sensitive and must match on both peers. Each peer points peer-address at the other's VLAN 4094 IP. AW 18 p.90–91
  • Every MLAG member must be a port-channel on each peer, even with one link per peer. The mlag number links them; keep the port-channel numbers the same too, for your own sanity. AW 18 p.92
  • reload-delay keeps ports errdisabled after a reboot (all but L3 and peer-link ports) until the peer has synced. reload-delay non-mlag lets routed ports come up first so routing settles before MLAGs rehash. AW 18 p.94
  • Dual-primary (split brain): a heartbeat to the peer's management IP. If the peer link dies but the heartbeat still answers, the secondary errdisables its ports after the delay. AW 18 p.94, 96
  • VARP: both MLAG peers answer ARP for the same virtual IP with one global virtual MAC, and both route, so traffic is routed on whichever switch receives it and never crosses the peer link. No protocol, no timers, so failover has no lag. AW 19 p.103–104
  • VRRP: one master routes, backups listen; only the master sends advertisements (every 1 s by default). Use it where VARP can't go, such as routed Ethernet ports. AW 19 p.99–100, 104
  • Routed subinterfaces (Ethernet1.100) give one VLAN-tagged L3 link per VRF on a routed port.

  • p.89 Peers should run the same EOS. Mixed versions peer only if they're on the MLAG ISSU compatibility list; check with show mlag issu compatibility flash:<image>. The output lists suggested versions when the answer is no.
  • p.90 Peer-link build order: port-channel trunk, VLAN 4094 with a trunk group on both the VLAN and the peer-link port-channel, STP off for that VLAN, SVI with no autostate, then the mlag configuration block.

  • p.94 No preemption: a returning former primary stays secondary. There's no command to force a failover short of a reload. Default reload-delay is 300 s on fixed switches and longer on chassis (Arista suggests about 720 s for big chassis).

  • p.97 Read the warnings reload prints before an MLAG upgrade (incompatible version, STP not restartable yet, active-partial MLAGs, reload-delay too low, peer still errdisabled). reload now skips them, so don't use it here.
  • p.97–98 Only the primary runs STP. A priority change on the secondary does nothing until a failover, then suddenly takes effect. Keep STP running with MLAG; it's the backstop against someone looping a desk switch.

Arista Warrior ch. 19, First-Hop Redundancy: notes by page

  • p.99–100 VRRP is the open standard (RFCs 2338, 3768, 5798) and works like HSRP. A virtual router is a VRID (1–255) plus its virtual IPs. The same VRID can be reused on different interfaces, but not the same VRID and VIP pair. show vrrp shows nothing until ip routing is on.
  • p.99–100 Defaults: advertisements every 1 s, preemption on, priority 100. The virtual MAC is 0000.5e00.01xx where xx is the VRID in hex.
  • p.101 Preemption can be turned off per group, or delayed: a minimum delay before taking over, and a separate delay after a reload. Advertisement timers can be changed, and default puts each setting back.
  • p.101 Priority runs 1–254, higher wins. If a master already exists with the same priority, a new router stays backup. Raise priority to make a router master.
  • p.102 With preemption on, the higher-priority router takes master back as soon as it returns. EOS won't accept a VIP that equals an interface's own IP.
  • p.102 A group can hold several VIPs: add extras as secondary. Authentication can be clear text (visible in show output) or MD5 (hidden in the running config). Configure the same on every router in the group.
  • p.103 Tracking: create a track object on an interface's line protocol, then have the VRRP group either decrement its priority or shut down when it goes down. A decrement must drop the master below the backup's priority to cause a failover.
  • p.103 A VRRP group can be shut down on its own. show vrrp brief is the summary view in busy configs. show track lists objects and what tracks them; spell out brief, because a shortened form is read as an object name.
  • p.103–104 VARP (L3 anycast gateway): every switch answers ARP and gratuitous ARP for the shared VIP with one virtual MAC. Hosts use whichever reply they get first, so there's no real load balancing, but with MLAG traffic is routed locally on both switches and stays off the peer link.
  • p.104 VARP setup is two lines: the global virtual-router MAC (same on both switches, and it must have the locally administered bit set; 00:1c:73:00:00:99 is the usual one), then the VIP under each SVI. It works only on VLAN interfaces. You can ping the VIP. Several VIPs per VLAN are allowed. The VIP is never used as a source address except for gratuitous ARP.

The book shows EOS 4.21 VRRP syntax (vrrp 10 ip, vrrp 10 priority, vrrp 10 track, vrrp 10 authentication, vrrp 10 timers advertise). Current EOS uses vrrp 10 ipv4, priority-level, tracked-object, peer authentication and advertisement interval; many releases still accept the old forms. Check with vrrp 10 ? on your lab's EOS. For EVPN fabrics, ip address virtual (D6.2) is the anycast-gateway form of the same idea.

Know

Know

  • VXLAN adds 50 bytes (outer Ethernet 14 + IP 20 + UDP 8 + VXLAN 8). Set fabric links to 9214 so 9000-byte host frames still fit.

show mlag says "inconsistent". Where do you look first?

The peer link fails but both switches are up. What stops both becoming primary and what happens next?

You configured ip virtual-router address 10.10.10.1 on Vlan10 on both leaves, but hosts can't reach their gateway. What's missing?

The global ip virtual-router mac-address, the same on both leaves. Without it show ip virtual-router reports the MAC isn't configured and nothing answers ARP for the VIP. (AW ch.19 p.104)

VRRP master has priority 105, backup 100. You track the master's uplink with decrement 5. The uplink fails. Does the backup take over?

No. 105 − 5 = 100 ties with the backup, and an equal priority doesn't displace a working master. Decrement by more than the gap (for example 10). (AW ch.19 p.101, p.103)

A 9000-byte ping between hosts on different leaves fails; 1400 works. What's the likely cause?

An underlay link with MTU below 9050. VXLAN adds 50 bytes. Set fabric links to 9214 and re-test with size 8972 df-bit.

Why do spines in an eBGP L3LS usually share one ASN?

A route learned from one spine can't be re-advertised by a leaf to another spine and accepted (same ASN in the path), which stops leaf-to-spine-to-leaf-to-spine path hunting, and the config stays uniform.

Overlay Protocols

The center of the Engineering exam. VXLAN is the data plane: a 24-bit VNI in a UDP header, between VTEP loopbacks. EVPN is the control plane: BGP routes that tell VTEPs which MACs and IPs sit behind which VTEP, and who wants floods. Read R1 after this domain.

6.1

VXLAN: VTEPs, VNIs, HER, VXLAN with MLAG

Know

  • VTEP = the Vxlan1 interface, sourced from a loopback. UDP port 4789. The VNI is 24 bits (about 16.7 million segments) against 12 bits for a VLAN, so different tenants can reuse a VLAN number on different VNIs. AW 21 p.110–111, 113
  • VXLAN is stateless encapsulation, not a tunnel that comes "up": a VTEP wraps the frame in UDP/IP and sends it to the remote VTEP's IP. Nothing is up or down until traffic flows. AW 21 p.112
  • L2 VNI maps a VLAN to a VNI (bridging). L3 VNI maps a VRF to a VNI (routing between VTEPs in symmetric IRB).
  • BUM (broadcast, unknown unicast, multicast) handling: HER sends a copy to each VTEP in the flood list. The control plane decides how that list is built: manual, CVX, or EVPN type-3 routes. A multicast underlay is the other option, but VXLAN with MLAG and VXLAN routing need HER or EVPN. AW 21 p.112–114
  • Flood lists: a default list (vxlan flood vtep) applies to every mapped VLAN; a per-VLAN list (vxlan vlan 10 flood vtep) overrides it for that VLAN. AW 21 p.114–115
  • MLAG pair = one logical VTEP. Both peers use the same Loopback1 IP and identical VLAN-to-VNI maps and flood lists; Loopback0 stays unique. Add a routed link between the peers so a peer that loses its uplink still reaches the fabric. AW 21 p.118–119
  • Data-plane learning: without EVPN, VTEPs learn remote MACs from received frames.

Arista Warrior ch. 21, VXLAN: notes by page

  • p.110–111 Terms: VXLAN segment (an L2 overlay network), VNI (its 24-bit ID), VTEP (the device that encapsulates and decapsulates), VXLAN gateway (a hardware VTEP for devices that can't speak VXLAN), underlay (the routed network) and overlay (the L2 segments on top). Arista's VXLAN is done in hardware, so not every platform or virtual EOS supports the data plane.
  • p.112 Think of each VTEP as a port on one big switch whose fabric is the L3 network: unknown destinations are flooded to every VTEP in the segment, replies are unicast, and VTEPs learn which MAC sits behind which VTEP, just like a switch's MAC table.
  • p.113 HER: the ingress VTEP copies each BUM frame to every VTEP in the flood list. A good VNI plan encodes meaning, for example tenant digits plus the VLAN.
  • p.114 Three ways to run the control plane: manual flood lists, CVX, or a routing protocol (EVPN). Manual config: Vxlan1 source interface on a loopback, VLAN-to-VNI maps, flood lists. The add keyword appends a VTEP; leaving it out overwrites.
  • p.115 Per-VLAN flood lists take priority over the default list. show vxlan flood vtep marks VLANs that fall back to the default list. EOS adds vxlan udp-port 4789 to the config by itself.
  • p.116 Verify with show vxlan vtep (recently active remote VTEPs only), show vxlan address-table (MAC behind remote VTEP IP), and show vxlan vni (VNI to VLAN, and the source of the mapping).
  • p.116–117 CVX (CloudVision eXchange, a vEOS instance running service vxlan) learns every VTEP and its VNIs and pushes flood lists to all of them. On each VTEP: management cvx with the server address, and vxlan controller-client on Vxlan1. Check with show vxlan controller status (should say Established), show management cvx, and on CVX show cvx service Vxlan (capital V) and show cvx connections.
  • p.117 With CVX, MAC-to-VTEP entries are also shared, so a VTEP can know a remote MAC before seeing any traffic from it (type RECEIVED in the address table), which cuts flooding. A VTEP ignores its own address in a flood list. The book leaves EVPN out; for EVPN use 6.2 and the AVD docs.
  • p.118–119 VXLAN with MLAG: both peers share one Loopback1 address and have identical VXLAN config, so the pair appears as a single VTEP and a single logical switch. A routed link between the peers lets one peer reach the fabric if its uplink fails. If a peer fails, LACP rehashes. If one peer's uplink and the other peer both fail, the pair is cut off, which is why you want more ECMP uplinks.

6.2

EVPN overlay: route types, VRFs, IRB

Know

  • Overlay sessions run between Loopback0 addresses (eBGP multihop to the spines, or iBGP to route reflectors), address family evpn, with extended communities.
  • Spines in an eBGP overlay keep the original next hop: next-hop-unchanged. Otherwise traffic tunnels to the spine.
  • Type 2 MAC/IP: a host's MAC (and IP) behind a VTEP. Type 3 IMET: "send me floods for this VNI", builds the flood list. Type 5 IP prefix: subnets and external routes in a VRF.
  • RD makes a route unique; RT decides which MAC-VRF or IP-VRF imports it. AVD convention: RD = router-id:VNI, RT = VNI:VNI.
  • VLAN-based service: one EVI per VLAN. VLAN-aware bundle: one EVI with many VLANs, one RD/RT, Ethernet tag = VLAN.
  • Symmetric IRB: route at ingress and egress through the L3 VNI. Leaves only need the VLANs they host. Scales well. Asymmetric IRB: ingress routes and bridges into the destination VNI. Every leaf needs every VLAN; no L3 VNI.
  • Anycast gateway: ip address virtual with the same IP and virtual MAC on every leaf.
  • L2-only VLAN (30 here): VLAN plus VNI plus MAC-VRF, no SVI, nothing in the VRF.

6.3

EVPN multihoming (ESI, all-active)

Know

  • The standards-based alternative to MLAG: two (or more) leaves share an Ethernet Segment, identified by a 10-byte ESI, with no peer link.
  • Type 1 Ethernet A-D: per-ES (fast mass withdraw when the segment fails) and per-EVI (aliasing, so remote VTEPs load-balance to all leaves on the segment).
  • Type 4 Ethernet Segment: discovers the peers on an ES and elects the designated forwarder (DF), which alone forwards BUM to the host.
  • Both leaves must present the same LACP system ID so the host bundles them into one LAG.
  • DF election defaults to modulus (by VLAN). Preference-based election lets you pick the DF.

Configure (leaf3 and leaf4, same values)

interface Port-Channel5
   switchport mode trunk
   switchport trunk allowed vlan 10,20
   evpn ethernet-segment
      identifier 0000:0000:0303:0202:0101
      route-target import 03:03:02:02:01:01
   lacp system-id 0303.0202.0101
interface Ethernet5
   channel-group 5 mode active

! optional: choose the DF
   evpn ethernet-segment
      designated-forwarder election algorithm preference 200

Verify

  • show bgp evpn route-type ethernet-segment
  • show bgp evpn route-type auto-discovery
  • show bgp evpn instance (DF per VLAN, local ES)
  • show port-channel summary on the host side

Exam traps

  • Different ESI or LACP system ID on the two leaves: the host's LAG won't bundle, or BUM is duplicated.
  • Using ESI multihoming on ports that are also MLAG ports. Pick one per segment.

Practice: D6

host1 (VLAN 10, leaf1) pings host2 (VLAN 10, leaf3) fine but can't ping 10.20.20.11 (VLAN 20, leaf3). What do you check?

Bridging works, routing doesn't, so check the L3 parts: vxlan vrf TENANT-A vni 50001 on both, the VRF RD/RTs in BGP, ip virtual-router mac-address, and show ip route vrf TENANT-A on leaf1 for a type-2 host route or type-5 subnet pointing at leaf3's VTEP.

leaf1's VLAN 10 flood list holds 10.255.1.5. You type "vxlan flood vtep 10.255.1.7". What's in the list now?

Only 10.255.1.7. Without add the command replaces the list. Use vxlan flood vtep add 10.255.1.7. (AW ch.21 p.114)

Right after configuring static HER, show vxlan vtep is empty. Is VXLAN broken?

Not necessarily. That command lists VTEPs that have exchanged traffic recently. Send traffic (ping between hosts), then check again, and confirm the configured list with show vxlan flood vtep. (AW ch.21 p.116)

Which EVPN route type tells a VTEP to add another VTEP to its flood list?

Type 3, Inclusive Multicast Ethernet Tag (IMET).

Leaves receive EVPN routes but import none of them. The first thing to check?

Route targets. Make sure extended communities are sent (send-community or send-community extended) on every hop, and that import RTs match export RTs.

Symmetric or asymmetric IRB for 200 VLANs across 40 leaves where each rack uses 10 VLANs?

Symmetric. Each leaf only configures its own 10 VLANs plus the L3 VNI. Asymmetric would need all 200 VLANs and SVIs on every leaf.
